# Мониторинг сетевого оборудования

Единственный источник требований: `docs/TZ.md`. Фичи называются по их ID (например, `MAP-03`). Менять объём может только заказчик.

## Общие файлы

- `docs/TZ.md`: требования, читать только нужные разделы.
- `docs/architecture.md`: архитектура и контракты, ведёт `architect`.
- `docs/assumptions.md`: реестр допущений и неподтверждённых фактов.
- `docs/reports/`: отчёты по задачам.

## Непреложные правила

- Система работает без интернета: никаких внешних URL и ресурсов во время работы.
- OID, порты и команды не выдумываются. Нет подтверждения значит «не подтверждено».
- Всё специфичное для оборудования живёт в профилях, а не в коде.
- Секреты не попадают в логи, ответы API и Excel.
- Проверка только на эмуляторах и заглушках. Что нельзя проверить здесь (Windows, реальное оборудование), перечисляется в отчёте и не выдаётся за проверенное.
- Агент работает только в своей зоне. Нужно изменение в чужой зоне или в контракте: сообщить в отчёте, а не править самому.

## Пайплайн задачи

Управляет основная сессия, она же единственная делает коммиты.

1. `architect`: уточняет контракты и план задачи.
2. Разработчик по зоне (таблица в разделе 11 ТЗ) реализует план и пишет тесты.
3. `compliance-auditor`: механическая проверка правил.
4. `qa-verifier`: тесты и критерии готовности фич.
5. `code-reviewer`: финальное ревью.
6. `tech-writer`: отчёт и реестр допущений.

Замечание на шагах 3–5 возвращает работу разработчику. После 2 кругов без результата решение принимает заказчик. Автор реализации сам её не принимает.

## Отчёт каждого агента

Кратко: что сделано, что не проверено, что нужно от человека.
