## Решения, принятые при реализации

- Кэша настроек нет: `Settings` читает значение при каждом вызове.
- `GET /api/settings` отдаёт `[{key, value, min, max}]`, `value` строкой. Порядок ключей задаётся сортировкой в Java (`String.compareTo`), не `ORDER BY` в БД. Строки `system_setting` без определения не показываются.
- `PUT /api/settings/{key}` с телом `{"value": "..."}`. Ключ сравнивается точно. Неизвестный ключ даёт 404 `NOT_FOUND` до проверки значения.
- Значение проверяется шаблоном `[1-9][0-9]{0,9}` и диапазоном. Иначе 400 `VALIDATION_FAILED` с сообщением «Целое число от X до Y» в `fields`. Число JSON принимается и приводится к строке. `true`, объект, массив, `null`, пустая строка и `"05"` дают 400. Тело не JSON-объект: 400 `BAD_JSON`.
- Оптимистической блокировки (`version`) нет. Столбца в `system_setting` нет. Правка идёт под `select ... for update`, журнал хранит старое значение, прочитанное под замком.
- Равное текущему значение: 200 без записи, без журнала и без события.
- Событие `SettingChanged` публикуется после фиксации транзакции (`AFTER_COMMIT`). Падение подписчика не валит ответ.
- Перезапуск не нужен ни для одного ключа.
- Границы §13.2 выбраны архитектурой (architecture §15 A-9), в ТЗ их нет. Это A-46.
- Правило замка устройства (§7.2, с `5b95af3`): только `FOR NO KEY UPDATE` или неключевой `UPDATE`, `FOR UPDATE` запрещён. Причина: тупик трапов (`FOR KEY SHARE` от FK `event.device_id` и `FOR UPDATE` в `StatusRecalculator`). Проверено прототипом на PostgreSQL 18.6: `FOR UPDATE` даёт 40P01, с `FOR NO KEY UPDATE` обе транзакции фиксируются. Правило внесено в пометки T3.10, T3.11, T4.14 и задачи 6.
- Мелочи ревью T1.06 (`count`/`page` без общей транзакции, размер значений, индекс) отложены в T3.23 (A-42).
