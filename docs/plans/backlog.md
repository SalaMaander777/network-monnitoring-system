# Бэклог микрозадач

Основание: `docs/TZ.md` v2.2, контракты: `docs/architecture.md` (далее «§»). Подробные карточки: `docs/plans/task-N.md`; для задач 2–8 их пишет `architect` перед началом задачи.

**Как читать.** «Группа» указывает параллельную дорожку внутри задачи, расшифровка и зоны файлов в разделе «Параллельность». Микрозадачи одной дорожки идут строго подряд. Фича в строке значит, что микрозадача реализует её или её часть; фича готова, когда выполнены все её строки. Пометка **[Ч]** значит, что автоматическая команда проверяет только то, что можно проверить здесь, остальное остаётся за человеком.

**Исполнитель.** Агенты по таблице раздела 11 ТЗ. Страницы интерфейса во всех задачах ведёт `map-frontend`: они входят в его зону в `.claude/agents/map-frontend.md`, а зона `backend-core` карту и интерфейс не описывает.

**Команда проверки.** У каждой микрозадачи своя команда из §12.1, по умолчанию `mvn -B -pl server -am test -Dtest=<Классы теста>`. Для задачи 1 они указаны в карточках.

Пометка для карточек задачи 3 (ревью T1.02): T3.05, T3.06, T3.17 и T3.21 следуют правилу «Общая БД JVM» §12.2. Тесты разделов и здоровья опроса (POLL-06, POLL-09) — `@IntegrationTest`, состояние `check_result_default` проверяют только после очистки `TestDb` и строк в нём, созданных другими классами, не ожидают; тест, создающий строку в разделе по умолчанию для проверки сигнала POLL-09, удаляет её сам в `finally`. Тесты T3.16, меняющие сроки хранения, возвращают настройки в `@AfterEach`.

Пометка для карточек задачи 3 (T1.06): удаление по сроку делит каждый модуль для своей таблицы (§4.3, §2.2): T3.16 удаляет только `event` (модуль `journal`), `audit_log` удаляет T3.23 в модуле `audit` (зона backend-core) тем же способом (пакеты по 10 000 строк, `retention.journal_days`, задание под `nm.jobs.enabled`). Запись `event` и `audit_log` сделана в T1.06 (`EventJournal`, `AuditLog` с `MANDATORY`, §7.2 «Запись журналов»): события статуса (T3.11) пишутся через `EventJournal` внутри транзакции пакета результатов, свой `insert into event` в `poll`/`status` запрещён. Поиск T3.15 читает `details` как `jsonb`, секретные поля в нём уже удалены `SecretFieldGuard`. С T1.07 (ревью T1.06): писатель результатов `status` (T3.10, T3.11) берёт замок строки устройства только `FOR NO KEY UPDATE` или неключевым `UPDATE device`, никогда `FOR UPDATE` (§7.2 «Замок строки устройства»); тест T3.11 с параллельной записью события и пересчётом статуса одного устройства без 40P01. Период `from`/`to` в `GET /api/events` (T3.15) проверяется `PeriodParams.check` (§5.1). Сроки `retention.*` (T3.05, T3.16, T3.23) читаются `Settings.getInt` при каждом запуске задания, без своего кэша и без подписки на `SettingChanged` (§13.2). Фильтры `audit_log` по `user_id` и `object_type` идут без своего индекса (только `ix_audit_ts`; решение ревью T1.06: объём ограничен `retention.journal_days`); T3.23 при нагрузочной проверке удаления меряет и `GET /api/audit` с фильтром на 1 млн строк и при выходе за 1 с запрашивает индекс у `architect` (миграция `V0323__`).

Пометка для карточек задачи 3 (ревью T1.03): тесты планировщика, цепочки результата, перезапуска и нагрузки (T3.09–T3.14, T3.17, T3.21, T3.22), включающие `nm.poll.enabled` или `nm.jobs.enabled`, следуют правилу «Фоновые задачи в тестах» §12.2 (`@DirtiesContext(AFTER_CLASS)`, `RestartableApp` в `try`-с-ресурсами). Тесты, двигающие время, используют `MutableClock` и не полагаются на его значение из другого метода (сбрасывается перед каждым). `DEBUG` только через `LogCapture.level(...)`.
